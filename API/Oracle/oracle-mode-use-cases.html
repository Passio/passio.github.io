1Architecture Overview

The Oracle-mode integration adds a second path for assignment authority alongside the existing Passio Transit pipeline. Three systems collaborate:

MDT
In-vehicle Mobile Data Terminal

Initiates all driver-driven actions: block selection, stop jumps, OOS toggle. Polls /liveStatus for authoritative state.

Navigator
Passio Back-end

Authoritative data store, business logic, and Oracle adapter. All DB access goes through the TDB API — no raw db.query calls. Exposes MDT surface under /:username/passioTransit/mdt.

Oracle
External ETA/Prediction Engine

Receives block assignments and GPS traces; returns predicted vehicle positions and trip updates. Navigator adapts all calls through oracleService/client.js.

TDB / MySQL
Relational Store — Mixed Sharding Strategy

Regular tables (e.g. bus, oracleBus, oracleSession) are single tables scoped to an agency via a userId foreign key — not date-sharded.
Log/append-only tables (e.g. oracleBusUpdateLog2, location, etaLog) are date-sharded: the physical MySQL table name encodes a date suffix from the row's datetime/created field (e.g. oracleBusUpdateLog220260101). Config "sharding": 10 means the first 10 characters of the ISO datetime (YYYY-MM-DD) form the shard suffix.

ℹ All MDT ↔ Navigator surface endpoints are mounted under /:username/passioTransit/mdt — see passioTransit/mdt/router.js. Every handler validates user.isOracleEtaEnabled = 1 before proceeding.

UC4 Dispatch sets the block to null (unassignment)

Handler
tdb update.after hook → oracleService/job/assignBlocksOnChange.js
Oracle call
POST /session/{id}/assign-block {block_id: null}
READ user (isOracleEtaEnabled) READ oracleSession {busId, day} WRITE bus/oracleBus (blockId=null — via Dispatch UI) WRITE oracleSession.blockAssignmentToOracleStatus = 'unassigned' Oracle: assign-block {null}
✏ Code-verified details
  • assignBlocksOnChange.js is not directly invoked by a Navigator controller here — it fires from the tdb update.after hook whenever bus.blockId changes, including Dispatch-driven changes.
  • Oracle payload: {block_id: null} at assignBlocksOnChange.js:83.
  • On Oracle success, blockAssignmentToOracleStatus → 'unassigned' (not null).
  • On Oracle failure, status → 'pending' so the reconciliation job retries.
  • oracleSession.blockId is cleared to null only on a successful non-null assignment; for unassignment only the status field is updated.

UC5 ⚠ Dispatch changes the routeStop — NOT sent to Oracle

⚠ Known gap: Navigator does not forward Dispatch-driven routeStopId changes to Oracle. Oracle is the authoritative source for vehicle position. The next /ask cycle will overwrite any Dispatch-set stop.
WRITE busTable.routeStopId (+ routeStopIdUpdated) WRITE oracleBusUpdateLog2 (audit only) No oracleSession write No Oracle HTTP call
✏ Code-verified details
  • The busUpdateHookForOracleService in bus/tdb.js only triggers the Oracle block-assignment path when blockId, archive, or outOfService changes. routeStopId is not in the trigger set.
  • The oracleBus/tdb.js hook writes oracleBusUpdateLog2 for every routeStopId/tripId change — this is an audit trail, not an Oracle notification.
  • On the next pushPositions tick, Oracle's vehicle_position overwrites the Dispatch-set stop.

6Validation vs. Production Mode

Every handler and daemon selects the target bus table using the same rule from oracleService/util.js:

const busTable = user.useOracleForAssignments ? busTables.bus : busTables.oracleBus
useOracleForAssignmentsTarget tableBehaviour
1 — Production bus Live assignment data; affects all consumers of the bus table
0 — Validation oracleBus Shadow table; MDT Oracle endpoints write here; pushPositions reads here; legacy bus flows are unaffected
✔
Both modes share identical Oracle-sync logic:
  • Same busUpdateHookForOracleService (wired from both bus/tdb.js:386 and oracleBus/tdb.js)
  • Same assignBlocksOnChange Oracle call path
  • Same oracleBusUpdateLog2 audit log writes for routeStopId/tripId changes
  • Same pushPositions tick logic (busTable pointer is the only difference)
